# Codex Task: Slice 2.5 — Retrieval Metadata Quality Hardening for RAGDocForge

## Project Name

RAGDocForge

## Slice Goal

Improve the retrieval-readiness quality of the artifacts generated by RAGDocForge after Slice 1 and Slice 2.

The current app successfully parses documents, scores RAG readiness, generates markdown, creates JSONL chunks, runs optional LLM analysis, and exports ZIP artifacts. However, the current retrieval metadata has quality problems:

1. Oracle object extraction produces false positives such as `A`, `THE`, `GENERAL`, `ORACLE`, `CAN`, `IS`, `RETURN`, `WARNING`, `NOTE`, and similar generic terms.
2. Chunk metadata inherits too much document-level metadata, causing every chunk to appear related to every table, procedure, function, and error.
3. Quality scoring can rate a document as `GOOD` even when blocking issues exist.
4. Title extraction may choose generic headings such as `Summary` instead of a useful document title.
5. Very small chunks are produced and should often be merged.
6. Markdown YAML front matter is too large and noisy.
7. LLM suggestions need better grounding and confirmation flags.

This slice must harden the metadata, scoring, chunking, and output formatting so generated artifacts are more reliable for downstream vector search, Qdrant ingestion, hybrid retrieval, metadata filtering, and category-weighted retrieval.

## 3.5 Add Object Name Validation Function

Implement:

```python
def normalize_oracle_identifier(name: str) -> str:
    ...

def is_valid_oracle_object_name(name: str) -> bool:
    ...

def object_confidence_score(name: str, evidence_type: str | None) -> float:
    ...
```

Validation requirements:

```text
Valid Oracle object names should usually:
- Be uppercase after normalization
- Be 3 to 128 characters
- Match pattern: ^[A-Z][A-Z0-9_$#]*(\.[A-Z][A-Z0-9_$#]*)?$
- Contain underscore, OR
- Be schema-qualified, OR
- Have a known EBS/custom prefix, OR
- Be directly captured from CREATE PACKAGE / CREATE PROCEDURE / CREATE FUNCTION
```

Reject if:

```text
- Name is in ORACLE_OBJECT_STOPWORDS
- Name length < 3
- Name is purely numeric
- Name contains spaces
- Name is a generic SQL keyword
- Name is a generic English word
- Name has no underscore and no schema qualifier and no strong CREATE evidence
```

Special case:

```text
- Procedure/function names may not always have underscores.
- Accept non-underscore procedure/function names only when extracted from strong PL/SQL signature evidence:
  CREATE OR REPLACE PROCEDURE name
  PROCEDURE name(...)
  CREATE OR REPLACE FUNCTION name
  FUNCTION name(...)
```

## 3.6 Strong SQL Extraction Patterns

Only extract table/view names from strong SQL contexts.

Accepted patterns:

```text
FROM object_name
JOIN object_name
UPDATE object_name
INSERT INTO object_name
DELETE FROM object_name
MERGE INTO object_name
TABLE(object_name)
```

Do not extract random uppercase prose words.

Implement robust regex with case-insensitive matching but normalized uppercase output.

Examples that must pass:

```sql
SELECT *
FROM gl_interface
WHERE group_id = :group_id;

SELECT h.je_header_id
FROM apps.gl_je_headers h
JOIN gl_je_lines l ON h.je_header_id = l.je_header_id;

UPDATE xxgl_interface_stg
SET status = 'E'
WHERE batch_id = :batch_id;

MERGE INTO gl_interface gi
USING xxgl_stage xs
ON (gi.reference1 = xs.reference1);
```

Expected objects:

```text
GL_INTERFACE
GL_JE_HEADERS
GL_JE_LINES
XXGL_INTERFACE_STG
XXGL_STAGE
```

---

## 3.7 PL/SQL Extraction Rules

Extract packages, procedures, and functions from strong PL/SQL signatures.

Patterns:

```text
CREATE OR REPLACE PACKAGE package_name
CREATE OR REPLACE PACKAGE BODY package_name
CREATE OR REPLACE PROCEDURE procedure_name
CREATE OR REPLACE FUNCTION function_name
PROCEDURE procedure_name(...)
FUNCTION function_name(...)
package_name.procedure_name
```

Requirements:

```text
- Package names should be stored in packages.
- Procedure names should be stored in procedures.
- Function names should be stored in functions.
- package_name.procedure_name should add package_name to packages and procedure_name to procedures only when both names pass validation.
```

---

## 3.8 Confidence Thresholds

Add thresholds:

```python
MIN_OBJECT_CONFIDENCE = 0.70
MIN_CHUNK_OBJECT_CONFIDENCE = 0.75
```

Suggested confidence scoring:

```text
CREATE PACKAGE / PROCEDURE / FUNCTION: 0.98
FROM/JOIN/UPDATE/INSERT/MERGE/DELETE SQL context: 0.90
Schema-qualified object: 0.90
Known EBS/custom prefix with underscore: 0.85
Package member call: 0.80
Weak uppercase text match: 0.30
```

Final extracted lists should include only candidates with confidence >= `MIN_OBJECT_CONFIDENCE`.

Do not expose weak matches as authoritative metadata.

# 4. Document-Level vs Chunk-Level Metadata Separation

## 4.1 Current Problem

Each chunk appears to inherit the full document-level table/procedure/function/error list. This pollutes chunk metadata and makes retrieval filtering unreliable.

## 4.2 Required Schema Change

Update `RagChunk` in:

```text
ragdocforge/schemas/chunk_models.py
```

Add explicit separation:

```python
class RagChunk(BaseModel):
    chunk_id: str
    doc_id: str
    source_file: str
    text: str
    section: str | None = None

    erp_module: str
    doc_type: str
    business_process: str | None = None

    token_estimate: int

    # Document-level metadata inherited for filtering
    doc_tables: list[str] = []
    doc_views: list[str] = []
    doc_packages: list[str] = []
    doc_procedures: list[str] = []
    doc_functions: list[str] = []
    doc_error_messages: list[str] = []
    doc_keywords: list[str] = []

    # Chunk-local metadata extracted only from this chunk text
    chunk_tables: list[str] = []
    chunk_views: list[str] = []
    chunk_packages: list[str] = []
    chunk_procedures: list[str] = []
    chunk_functions: list[str] = []
    chunk_error_messages: list[str] = []
    chunk_keywords: list[str] = []

    rag_priority: str = "medium"
    metadata_confidence: float = 1.0
```

Backward compatibility:

```text
If existing code expects tables/views/packages/procedures/functions/error_messages,
either:
1. keep them as deprecated aliases mapped to chunk-level lists, or
2. include compatibility properties.
```

Preferred behavior:

```text
- `chunk_tables` etc. should be used for chunk-specific retrieval metadata.
- `doc_tables` etc. should be used only for broad document context.
```

# 7. Minimum Chunk Size Merging

## 7.1 Current Problem

Very small chunks are generated, such as heading-only or one-question chunks. These are weak for standalone retrieval.

## 7.2 Add Minimum Chunk Size

Update chunker defaults:

```text
chunk_size_tokens = 700
chunk_overlap_tokens = 100
min_chunk_tokens = 120
```

Allow UI to expose `min_chunk_tokens` later, but for this slice it can be a constant or optional parameter.

## 7.3 Merge Rules

After initial heading-aware splitting:

```text
If chunk token estimate < min_chunk_tokens:
    merge with next chunk when possible.
Else if last chunk < min_chunk_tokens:
    merge with previous chunk.
```

Do not merge if the chunk is a standalone structured artifact:

```text
- SQL code block longer than 40 tokens
- Markdown table longer than 5 rows
- Error catalog entry with an explicit ORA-/FRM-/APP- code
```

Add helper:

```python
def should_preserve_small_chunk(text: str) -> bool:
    ...
```

Preserve if:

```text
- Contains ORA-\d+
- Contains FRM-\d+
- Contains APP-\d+
- Contains REP-\d+
- Contains fenced SQL code block
- Looks like a table with 5+ rows
```

# 18. Important Design Principle

This slice should make RAGDocForge stricter, not more generous.

Prefer this behavior:

```text
It is better to omit uncertain metadata than to include noisy false positives.
```

Downstream retrieval quality depends more on clean metadata than maximum recall. For Oracle EBS support documents, false object metadata is especially harmful because table/package names are often used for metadata filters, reranking, routing, and answer grounding.
